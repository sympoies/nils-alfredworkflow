# Development log - 2026-06

## 2026-06-26 - Cambridge provisions Playwright browsers by native download

**Result**

- `cambridge_runtime_install_browsers` no longer shells out to `playwright install
  chromium`. A native path downloads the Chrome-for-Testing artifact directly and extracts
  it with `ditto`/`unzip`, provisioning both chromium and the headless shell into the
  Playwright cache, with the Playwright installer kept as a fallback.
- The bootstrap honors `PLAYWRIGHT_DOWNLOAD_HOST` and `PLAYWRIGHT_BROWSERS_PATH` (and, after
  the follow-up, `PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST` with the same precedence Playwright
  itself uses), bounds the download with `curl --max-time`, sizes the stale window to the
  full native download budget, and registers native installs in Playwright's
  `.links/` browser-GC registry.

**Why / context**

- This is the root cause of the repeated "Installing Cambridge runtime..." loop users hit:
  Playwright's bundled out-of-process downloader was observed wedging indefinitely on macOS
  after a *completed* download (0% CPU, idle event loop), leaving a partial browser behind.
  Every retry re-entered the same wedge.
- Registering with the browser-GC registry matters because the Playwright cache is shared:
  another project running `npx playwright install` would garbage-collect browsers this
  workflow installed outside the registry, forcing a re-bootstrap that looked random.
- The stale window had to account for `native_count * install timeout + buffer`, not a
  single timeout, or a slow but progressing two-browser install is killed mid-progress and
  pushed back into the failed path.

**Evidence**

- PRs #207 and #208; `scripts/tests/cambridge_runtime_native_install.test.sh` covers the
  native path, and download-host and GC-registration tests were added with the follow-up.

**Links**

## 2026-06-22 - Google media transfers get their own deadline, and redaction covers more schemes

**Result**

- Drive media transfers and Gmail sends carry request-level five-minute deadlines while
  metadata calls keep the short timeout; `Authorization` schemes are parsed as HTTP tokens
  and AWS-style credential and signature tails are redacted.

**Why / context**

- One timeout cannot serve both call classes: a metadata call that takes 30 seconds is
  broken, while a large Drive upload that takes 30 seconds is normal. Applying the short
  timeout to transfers made large files impossible to move.
- The redactor previously matched on a `Bearer` prefix, so any other scheme passed through
  verbatim into error output.

**Evidence**

- PR #203.

## 2026-06-21 - A workspace-wide sweep repairs latent security, correctness, and reliability bugs

**Result**

- Security: non-`Bearer` `Authorization` schemes (Basic, Negotiate) are redacted in the
  shared error redactor; the server-controlled file name in google-cli Drive download is
  sanitized; token and credential files are written `0600` (directories `0700`) on Unix.
- Correctness: `market-cli` numeric expressions honor operator precedence, so `2+3*4` is
  14 rather than the left-to-right 20.
- Reliability: HTTP request timeouts were added to the wiki, spotify, steam, youtube, brave,
  and google clients, which had used `reqwest::blocking::Client::new()` with no timeout;
  the cambridge bootstrap gained an atomic spawn lock and PID-reuse verification;
  `workflow-common` usage logging writes a per-process temp file; `randomer-cli` bounds
  `--count`; `workflow-readme` image extraction skips fenced code blocks.

**Why / context**

- The redaction gap leaked the credential on every CLI error path, which is the highest
  impact item in the set: error output is exactly what a user pastes into an issue.
- A client with no timeout does not fail on a stalled server, it hangs, and a hung Script
  Filter presents to the user as Alfred being broken rather than the workflow.
- PID reuse is a real failure mode for a liveness check that stores a bare PID: a recycled
  PID makes a dead bootstrap look alive forever.

**Evidence**

- PR #202; each fix landed with regression coverage, including three new cambridge shell
  tests and the stale-window edge cases from #201.

**Links**

- <https://github.com/sympoies/nils-alfredworkflow/pull/202>

## 2026-06-21 - The Cambridge readiness check is repaired and coupled to the install timeout

**Result**

- The Playwright bootstrap pins the workflow-local package exactly, shares bootstrap
  helpers between the setup script and the packaged workflow path, and verifies readiness by
  launching headless Chromium. The unsupported `Browser.process()` call was dropped in
  favor of `chromium.executablePath()`, and the stale window is now derived from the install
  timeout through `cambridge_runtime_effective_stale_seconds` plus a new
  `CAMBRIDGE_RUNTIME_BOOTSTRAP_STALE_BUFFER_SECONDS` (default 120).

**Why / context**

- Checking `executablePath` alone says a file exists, not that a browser can start; a
  partially extracted browser passed that check and failed at query time.
- The readiness check itself then broke in a way only a real Node run could show: a
  Playwright `Browser` exposes no `process()`, so the check threw
  `browser.process is not a function` *after* a successful launch and reported the runtime
  unavailable. The stubbed-node test could not catch it, which is why real-node regression
  tests were added.
- Without the coupling, raising `CAMBRIDGE_PLAYWRIGHT_INSTALL_TIMEOUT_SECONDS` still let
  the fixed 600s stale window kill an install that was still making progress.

**Evidence**

- PRs #200 and #201; #201 also resolved the post-merge review threads on #200.

**Links**

- <https://github.com/sympoies/nils-alfredworkflow/pull/200>
- <https://github.com/sympoies/nils-alfredworkflow/pull/201>

## 2026-06-17 - Standalone CLI binaries ship alongside the workflow bundles

**Result**

- A manifest-driven `nils-alfred-cli` tarball builder with its own audit produces standalone
  binaries across Linux and macOS release targets, publishes portable checksums generated
  from the `dist` directory, and dispatches a Homebrew tap formula update after the GitHub
  Release is published.

**Why / context**

- The CLIs are useful outside Alfred, and requiring a Rust toolchain to use them made that
  claim theoretical. A tarball plus a tap formula is what makes it real for a non-Rust user.
- Checksums are generated from `dist` so the published asset references a basename rather
  than a build-host path, which is what lets a downloaded file be verified at all.
- Turso-dependent CLIs are excluded from the cross-target bundle because their native
  dependency does not cross-build cleanly; release build scripts also had to stay
  compatible with macOS Bash 3.2.

**Evidence**

- PRs #197 (release flow), #198 (matrix fix), and #199 (portable checksums); the tarball
  shell test covers the portable checksum contract.

**Links**

- <https://github.com/sympoies/nils-alfredworkflow/pull/197>

## 2026-06-15 - Shared CLI plumbing replaces per-crate copies

**Result**

- `workflow-common` gained a shared `ScriptFilterOutputModeArg` (behind an opt-in `clap`
  feature) adopted by twelve Script Filter CLIs, a shared `AppError` built on the existing
  `CliErrorKind` adopted by every workflow CLI across three batches, a clap value-enum
  `OutputMode`, and an opt-in blocking HTTP client builder for timeout and User-Agent
  setup. `google-cli` routed its error kind, redaction, and envelope assembly through the
  same helpers.

**Why / context**

- The migrated code was byte-identical across crates: the same `OutputModeArg` enum, the
  same `ErrorKind`/`AppError` pair, the same `error_kind_label` helper. Sixteen copies meant
  a contract fix had to be applied sixteen times, and the timeout gaps repaired in #202 are
  what that costs in practice.
- Behavior was held constant deliberately: emitted envelopes, `NILS_*` codes, exit codes,
  and messages are byte-identical after each batch, so the refactor is reviewable as a
  no-op and any diff in output is a bug rather than a decision.
- Per-request HTTP policy stayed local; only the client builder is shared, because timeouts
  differ per call class (see the Drive and Gmail deadlines the following week).

**Evidence**

- PRs #186 (output mode arg), #191, #192, #193 (AppError batches under issue #188), #194
  (google alignment), #195 (HTTP builder), and #196 (shared output mode enum).

**Links**

- <https://github.com/sympoies/nils-alfredworkflow/pull/191>
- <https://github.com/sympoies/nils-alfredworkflow/pull/193>

## 2026-06-12 - Dependabot cargo and actions updates are grouped weekly

**Result**

- Cargo minor and patch updates are grouped into one weekly pull request, as are GitHub
  Actions updates; major versions still open individual pull requests.

**Why / context**

- Each dependency bump in this repository requires a third-party artifact refresh and a full
  CI cycle. Ungrouped, a five-bump week costs five serialized refreshes, each of which
  invalidates the previous one's lockfile fingerprint.
- Majors stay separate because they can require adaptation (see the keyring 4 move), and
  grouping them would block four harmless bumps behind one migration.

**Evidence**

- PR #184, mirroring the identical configuration in the sibling `nils-cli` repository.

**Links**

- <https://github.com/sympoies/nils-alfredworkflow/pull/184>

## 2026-06-01 - Project skills adopt the `project-` prefix and memo moves to nils-memo 1.0.0

**Result**

- Both project skills were renamed to `project-pin-crates` and `project-release-workflow`
  (directories, scripts, test files, and skill metadata), and `AGENT_DOCS.toml` opted in to
  the `[skills] enforce_name_prefix` lint.
- The memo dependency moved from `nils-memo-cli` `=0.8.3` to the published `nils-memo`
  `=1.0.0`, with the library import, pin-skill target, docs, and workflow metadata updated

**Why / context**

  the 1.0.0 contract-namespace change does not reach this repository's surface; that is
  what made the migration safe to take as one bump.

**Evidence**

  migration was validated with `cargo test -p nils-memo-workflow-cli` (47 passed), the pin
