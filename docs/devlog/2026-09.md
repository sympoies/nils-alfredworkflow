## 2026-09-25 - Gave google-cli a governable account lifecycle

### Result

- `auth default <account>` makes a stored account or alias the default.
- `auth add --remote --step 2 --callback-url-stdin` takes the whole redirected
  URL on stdin, decodes the code, and reports a denied consent.
- `auth remove --revoke` revokes the refresh token at Google before forgetting
  it, treats `invalid_token` as revoked, and keeps the account on any other
  failure. `auth credentials set --revoke-uri` overrides the endpoint.

  and the current second.

### Why / context

  (serenvia/dsh-bots#50). A `--code` argument exposes the one-time code in the
  process list, the CLI had no way to change the default account, and removal
  left the grant live at Google.

### Evidence

- New `auth_account_lifecycle` integration tests failed on the old CLI and pass
  now, including a local HTTP endpoint for the revoke success, already-invalid,
  and failure paths.
- The complete local pre-commit gate passed on the candidate source.

## 2026-09-14 - The dependabot apply workflow could not find its own pull request

### Result

- Both jobs in `dependabot-third-party-apply.yml` selected the pull request with
  `gh pr list --head "${GITHUB_REPOSITORY_OWNER}:${HEAD_BRANCH}"`. `gh pr list` documents
  that the `<owner>:<branch>` form is *not supported*, so the filter matched nothing and
  both jobs took their "no open pull request" branch and exited 0. The automation was
  inert for every bump from the moment it shipped.
- The lookup is back to a bare `--head "${HEAD_BRANCH}"`, with the fork guard where it
  belongs: `--jq '[.[] | select(.isCrossRepository == false)][0]'`.

### Why / context

- The owner qualification was added the same day to close a review finding: `--head` alone
  matches a branch of that name in *any* repository, so an outsider's fork branch named
  like a Dependabot branch could be selected. The reviewer offered two remedies, the jq
  filter or an owner-qualified `--head`; both were applied, and the unsupported one
  silently won. The jq filter alone closes the finding.
- The failure mode is the dangerous kind: not an error, but a green run that reports
  "No open pull request for <branch>; nothing to apply" and does nothing. Nothing in the
  repository would have contradicted that message.
- This is the third instance in one day of the same root cause: an assumption about a
  neighbouring system carried into a change without being checked against that system.
  Previously it was cargo-deny's job-versus-workflow shape, then a devlog rule taken from
  the shared skill rather than this repository's own contract.

### Evidence

- Reproduced directly against this repository: `gh pr list --head docs/enable-devlog-backfill
  --state all` returns PR #234, while the same query with the branch qualified as
  `sympoies:docs/enable-devlog-backfill` returns nothing at all.
- `gh pr list --help` states the constraint outright:
  `Filter by head branch ("<owner>:<branch>" syntax not supported)`.
- The corrected form, bare `--head` plus the `isCrossRepository` filter, returns PR #234
  and drops cross-repository matches.
- `scripts/ci/ci-workflow-audit.sh` now rejects the owner-qualified form and requires the
  cross-repository filter. Both rules were confirmed red by reintroducing each defect into
  a copy of the real workflow, and the check output was inspected for `rg` flag-parse
  errors after an earlier version of the reject pattern was silently swallowed because it
  began with `--head`.

### Follow-ups

- The same fork-selection exposure and a branch-scoped concurrency group remain in the
  `nils-cli` original this was ported from; its merge gate is otherwise correct, because
  cargo-deny is a job inside its `CI` workflow rather than a separate workflow.
- Resolved: `sympoies/nils-cli#1718` applied the same `isCrossRepository` filter to both
  jobs and re-keyed the concurrency group on `workflow_run.head_sha`.
- Open: none of this has been observed on a real bump. The three bumps that would have
  exercised it were merged by hand in #236 before the lookup defect was found, so the
  corrected automation has never selected a Dependabot pull request. Tracked in #239,
  which lists what to confirm on the next bump; a green run proves nothing here, because
  every hand-off in this path fails by concluding success and doing nothing.

## 2026-09-14 - Dependabot bumps refresh their own third-party artifacts

### Result

- Two workflows ported from the sibling `nils-cli` repository automate the refresh that
  every Dependabot cargo bump needs: `dependabot-third-party-artifacts.yml` regenerates
  `THIRD_PARTY_LICENSES.md` and `THIRD_PARTY_NOTICES.md` unprivileged on `pull_request` and
  publishes them as an artifact, and `dependabot-third-party-apply.yml` commits those two
  paths onto the Dependabot branch through the Git Data API on `workflow_run`, then squash
  merges `dependabot/cargo/cargo-minor-patch-*` once both blocking workflows, `CI` and
  `cargo-deny`, have a completed successful run for that exact commit.
- `scripts/ci/ci-workflow-audit.sh` now requires those workflows and `cargo-deny.yml` to
  exist, requires the refresh step to carry the workflow-scoped `GITHUB_TOKEN`, keeps the
  unprivileged half read-only, rejects any `actions/checkout` in the privileged half, and
  pins both the cargo-deny merge gate and the workflow display names the gate selects on.

### Why / context

- Both generated artifacts embed the `Cargo.lock` SHA256 and the resolved crate versions, so
  a bump drifts them and the strict audit fails before the build phases even run. Every
  bump therefore needed a manual regeneration commit; the three open bumps at the time of
  this change (#227, #228, #229) had all been failing `validate` for that single reason.
- The split exists so the privileged half never executes pull-request content: the
  unprivileged job is the only place that runs anything from the bump, and the applying job
  writes only the two known paths, only onto the branch its run belongs to, and only while
  that branch head still matches the commit the refresh was generated for. CI then re-runs
  the strict audit on the result, so a bogus artifact fails rather than merges.
- A GitHub App token is required rather than `GITHUB_TOKEN`: a commit made with the default
  token starts no new workflow run, which would leave the refreshed commit permanently
  without CI results.
- Two divergences from the `nils-cli` original matter, and both are now pinned by the audit
  rather than left to memory. The generator here reads the bundled codex-cli release
  metadata from the GitHub Releases API, and the repository has required a workflow-scoped
  read token on every generator-bearing step since the codex authority work, so the refresh
  step carries it. And `cargo-deny` runs as its own workflow here rather than as a CI job:
  the ported gate watched only `CI`, which would have squash merged a grouped bump whose
  advisory and license check was red — precisely the situation the 2026-09-05 entry below
  records, where a group could not merge until two yanked and advisory-affected transitive
  patches were repointed.
- Auto-merge is deliberately scoped to the grouped minor/patch branch prefix. A major or
  single-crate bump is refreshed the same way but still waits for a human, because those
  are the ones that can change an API this workspace calls.

### Evidence

- `bash scripts/ci/ci-workflow-audit.sh --check` passes, and each new invariant was
  mutation-tested by deleting the whole rule from a copy of the audit and confirming
  `scripts/tests/ci_workflow_audit_routing.test.sh` goes red: the refresh-step token, the
  checkout ban, the read-only permissions pair, the cargo-deny merge gate, and the
  `cargo-deny` display-name pin all failed as expected.
- The workflow-existence loop entry survived that mutation, because each of those files is
  independently required by a content rule. The behavior it protects is still covered: the
  audit detects each of the three files being deleted, and the routing test asserts it.
- `scripts/tests/ci_workflow_audit_routing.test.sh` grew from three to eight cases.
- `bash scripts/local-pre-commit.sh` passes on the final tree.

### Follow-ups

- The applying half stays inert until `BOT_APP_ID` and `BOT_APP_PRIVATE_KEY` are configured
  for a GitHub App installed on this repository with `Contents: read and write`,
  `Pull requests: read and write`, and `Actions: read`. Until then it fails fast with that
  instruction and manual regeneration remains the fallback.
- Resolved later the same day: both secrets are configured for the `sympoies-bot` App
  (id `4665910`), whose org-wide installation includes those three scopes. The credential
  chain was verified before the automation could first fire — an installation token minted
  from the stored key reads this repository and lists its `ci.yml` runs, which is the
  Actions access the merge gate depends on.
- Worth knowing if this ever has to be re-provisioned: the `sympoies-reviewer` App
  (id `4756135`) that publishes review outcomes is a different identity and is not a
  substitute. It holds only `pull_requests: write` and `metadata: read`, and substituting it
  fails silently rather than loudly: without `actions: read` the artifact download fails,
  the outcome-guarded commit step is skipped, and the job still concludes success having
  applied nothing.

## 2026-09-14 - The development log is enabled and backfilled to the first commit

### Result

- `docs/devlog/` became a governed documentation category: a `README.md` contract, one
  month file per month, `scripts/devlog-search.sh` for lookup, and the entry-writing rule
  in `DEVELOPMENT.md`, `docs/MAINTENANCE.md`, `AGENTS.md`, and `AGENT_DOCS.toml`.
- Eight month files (2026-02 through 2026-09) were backfilled with 75 entries reconstructed
  from the 594 commits and the pull-request record since the repository opened on
  2026-02-10.

### Why / context

- The repository already records *what* changed (commits), *what is true now* (the root
  guides and `docs/specs/`), and *how a delivery went* (PRs, plans, reports). What it had
  no home for is why a decision was made and what evidence settled it, which is exactly
  what a future debugging session needs and what closed PRs bury.
- The backfill is deliberately not one entry per month: a month like 2026-02 contains 302
  commits and roughly twenty separable decisions, and collapsing them would lose the very
  detail the log exists to keep. Entries group by decision, not by date or by commit.
- Routine version bumps, screenshot refreshes, formatting repairs, and behavior-neutral
  dependency bumps were deliberately left out. They are recoverable from git and would bury
  the entries that are not.
- `.rumdl.toml` ignores MD036 for the month files only (`docs/devlog/YYYY-MM.md`) so the
  template's bold section labels stay non-headings; that keeps every `##` in a month file
  an entry heading and the month index scannable, while `docs/devlog/README.md` and any
  future non-entry doc in the directory keep the rule.
- The backfilled entries cite the commit and pull-request record rather than a live run,
  and `docs/devlog/README.md` says so explicitly rather than letting reconstructed evidence
  read as observed evidence.

### Evidence

- `bash scripts/local-pre-commit.sh` passed end to end (third-party artifact change gate,
  workflow lint, script-filter policy check, Node scraper tests, and workflow tests),
  including the new `scripts/tests/devlog_search.test.sh` among 26 script-test files.
- `bash scripts/docs-placement-audit.sh --strict` and
  `bash scripts/ci/markdownlint-audit.sh --strict` both pass with the new category; the
  markdown audit resolved local references across 150 files.
- `scripts/tests/docs_placement_audit.test.sh` gained a case asserting that
  `docs/devlog/*.md` is accepted while an ungoverned `docs/loose-note.md` still fails, so
  the allowlist widening cannot silently become a hole.

## 2026-09-10 - Weather retries Chinese city aliases when geocoding returns nothing

### Result

- When geocoding returns an empty result, four exact Chinese aliases (the Taichung
  spellings) are retried through the provider while the original results and errors are
  preserved.

### Why / context

- The upstream geocoder returns an empty list, not an error, for some Traditional Chinese
  city spellings, so the workflow showed "no results" for a correctly spelled city. A
  bounded alias retry fixes the observed case without turning the resolver into an
  open-ended fuzzy matcher.
- Preserving the original results and errors matters because the retry must not mask a
  genuine provider failure as a lookup miss.

### Evidence

  contract documented alongside them.
